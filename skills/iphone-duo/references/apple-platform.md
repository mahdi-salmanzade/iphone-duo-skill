# Apple platform reference

For the complete Duo HIG, supporting UI pages, and local illustrations fetched on October 2, 2026, use [Apple documentation and images](apple-docs.md) and [Design rules](design-rules.md). The dated toolchain and API notes below remain a separate snapshot.

Source snapshot checked **2026-09-30**. Open the relevant primary source and inspect installed declarations before writing new API calls. This reference records published guidance, not local SDK compilation or device-test results. Beta APIs and tooling can change.

The new API documentation is live; names below no longer depend solely on video transcriptions. Follow the guide's API links for the relevant feature rather than treating every addition as a migration requirement.

[Xcode 27.1 beta](https://developer.apple.com/documentation/xcode-release-notes/xcode-27_1-release-notes), released September 18 (27A9269), includes Swift 6.4, the iOS 27.1 SDK, and the Duo simulator; it requires macOS Tahoe 26.6 or later. Although Xcode 27.2 beta 2 is newer, its [release notes](https://developer.apple.com/documentation/xcode-release-notes/xcode-27_2-release-notes) still direct developers to Xcode 27.1 beta for Duo SDK and simulator support. Select a toolchain documented to support Duo. Recheck [Apple's releases](https://developer.apple.com/news/releases/) and the selected SDK/runtime before each migration. Apple's DocC pages may offer a Markdown version; otherwise their public documentation JSON can expose the text, declarations, and platform metadata behind the JavaScript page. ## SDK tiers and migration prerequisites

[Prepare your app for iPhone Duo](https://developer.apple.com/videos/play/tech-talks/111461/) describes three outcomes, decided by the SDK that linked the binary:

- Built with a pre-iOS 27 SDK: familiar iPhone sizing and aspect ratio, using less of each display.
- Built with the iOS 27 SDK: the inner-display app extends to the left of the status bar area.
- Built with the iOS 27.1 SDK: edge-to-edge content, vertical standard bars, and access to the new reserved-region APIs.

A JavaScript, Dart, or over-the-air update cannot change the linked SDK. Record the actual native binary's build toolchain; rebuilding with a supported SDK is required to change tiers.

The [iOS 27 release notes](https://developer.apple.com/documentation/ios-ipados-release-notes/ios-ipados-27-release-notes) require the scene-based lifecycle for apps built with the new SDK or they fail to launch. They also require a launch-screen configuration for App Store submissions built with iOS 27.0 or later. Inspect the listed supported plist keys and the project's generated configuration before upgrading. Scene lifecycle adoption and enabling multiple app windows are separate changes. The notes also list a `TabView` crash when its selection refers to a hidden or unavailable tab; check selection when adaptive navigation changes visibility.

## Baseline compatibility and layout

- **Local geometry and size classes.** The outer display has compact width; the inner display has regular width and height. The idiom remains `.phone`, and [iPad support is not required](https://developer.apple.com/forums/thread/847945). Use the scene or containing view's geometry for layout. Do not make orientation or a model identifier the layout classifier.
- **Screen access.** `UIScreen.main` is deprecated and ambiguous on a device with two displays. Prefer the [most local layout information](https://developer.apple.com/forums/thread/847909); use `UIWindowScene.screen` when a screen is actually needed, and `traitCollection.displayScale` for scale. Do not cache the screen across display transitions.
- **Safe areas and margins.** Both are asymmetric. Handle each edge independently, including Split View on either side. Keep ordinary interactive content within the safe area and allow background artwork beyond it. Edge-to-edge custom controls need reserved-region handling, not a guessed hinge gap or doubled left inset. Use `ConcentricRectangle` / `UICornerConfiguration` when fitting rounded UI to the changing screen shape.
- **Standard containers.** `NavigationSplitView` / `UISplitViewController` collapse on the outer display and tile or overlay on the inner display. Tabs, sheets, menus, and alerts adapt, but custom content still needs testing. SwiftUI sidebar opt-in uses `.tabViewStyle(.sidebarAdaptable)` with [`defaultTabBarPlacement(.sidebar)`](https://developer.apple.com/documentation/swiftui/view/defaulttabbarplacement(_:)); UIKit uses `tabBarController.sidebar.preferredPlacement = .sidebar`.
- **Full-screen compatibility.** [TN3192](https://developer.apple.com/documentation/technotes/tn3192-migrating-your-app-from-the-deprecated-uirequiresfullscreen-key) says that, starting with iOS/iPadOS 27, `UIRequiresFullScreen = YES` for an app linked against iOS 27 or later selects discrete resizing rather than an exemption from resizing. `UIRequiresFullScreenIgnoredStartingWithVersion` can disable this compatibility behavior starting at the specified version. The current Duo talk confirms that the key is honored while opening/closing still resizes the app. Inspect linkage and configuration; remove legacy compatibility only after adapting and verifying the affected app.
- **Orientation documentation conflict.** As of this snapshot, the preparation talk and Group Lab recap contain both “inner display ignores supported orientations” and “orientations are respected with inner-display scaling” statements. The written guide recommends size classes and scene geometry. Do not promise that an orientation lock fixes the window's shape or that every orientation mask is ignored. Test the actual binary's compatibility configuration through rotation, folding, and Split View. Games may lock orientation according to the HIG, but still need usable content in every pose.

## Product layout and presentations

[Design for iPhone Duo](https://developer.apple.com/videos/play/tech-talks/111466/) and the HIG favor a consistent hierarchy across sizes. Expand the existing layout; expose another hierarchy level when useful, as with list and detail, and preserve selection, drafts, and access to the same actions. Avoid a distinct screen implementation for each pose.

The outer display is wider and shorter than other iPhone displays, so system bars and status UI move to the side. On the inner display, bar layout depends on the container and configuration. The written preparation guide specifies:

| Presentation | Bar behavior |
| --- | --- |
| Split-view sidebar or content column | Horizontal |
| Split-view detail column | Vertical |
| Inspector | Horizontal |
| Outer-display sheet | Vertical by default |
| Inner-display centered or leading sheet | Horizontal |
| Inner-display trailing sheet | Vertical |

Request sheet placement with [`presentationPlacement(_:)`](https://developer.apple.com/documentation/swiftui/view/presentationplacement(_:)) or `UISheetPresentationController.preferredPlacement`. Sheets can adjust around a partial fold; verify the actual placement and anchor. For background continuity beneath bars, use `backgroundExtensionEffect()` / `UIBackgroundExtensionView` where appropriate. Immersive, non-scrolling content may span the full width while its controls avoid system regions; a scrolling foreground may remain inset over a full-width background.

## Bars and overflow

[Raise the bar with iPhone Duo](https://developer.apple.com/videos/play/tech-talks/111462/) ties automatic vertical arrangement to navigation containers, not standalone `UITabBar` / `UIToolbar` instances or hand-drawn bars.

- Placement runs from primary navigation (Back/Close: `cancellationAction`; UIKit `leftItemsSupplementBackButton = false`), to prominent actions (`topBarPinnedTrailing` / `pinnedTrailingGroup`), then remaining groups. Items overflow from bottom to top by default. [`visibilityPriority(_:)`](https://developer.apple.com/documentation/swiftui/toolbarcontent/visibilitypriority(_:)) / `UIBarButtonItem.visibilityPriority` (iOS 27.0+) change overflow priority. Group related actions instead of using fixed spacers; flexible spacers collapse vertically.
- [`axisBehavior(_:)`](https://developer.apple.com/documentation/swiftui/toolbarcontent/axisbehavior(_:)) / `UIBarButtonItem.axisBehavior` (iOS 27.1+) govern eligibility. Image items can use either axis; text-only and custom views default to horizontal-only. `.verticalPreferred` supports both and prefers vertical when both exist. [`.horizontalOnly`](https://developer.apple.com/documentation/swiftui/toolbaritemaxisbehavior/horizontalonly) items can disappear when no horizontal bar exists: essential actions need a tested reachable path. Provide both a symbol and a title; titles serve overflow, expansion, and accessibility. Prefer badges to inline status text.
- [`toolbarVerticalEdge`](https://developer.apple.com/documentation/swiftui/environmentvalues/toolbarverticaledge) / `traitCollection.verticalBarEdge` report the preferred edge **even when the bar is hidden**. They are layout signals, not visibility detectors. The hardware-aligned side does not simply mirror in right-to-left languages; test region coordinates and text direction separately.
- [`toolbarVerticalCompressionBehavior(_:)`](https://developer.apple.com/documentation/swiftui/view/toolbarverticalcompressionbehavior(_:)) / [`navigationItem.verticalBarCompressionBehavior`](https://developer.apple.com/documentation/uikit/uinavigationitem/verticalbarcompressionbehavior) (iOS 27.1+) choose whether toolbar items or tabs get space first; `.prefersToolbarItems` / `.prefersBarItems` favor task actions. Exercise overflow on the short outer display and with the keyboard visible.
- Put custom overflow actions in [`ToolbarOverflowMenu`](https://developer.apple.com/documentation/swiftui/toolbaroverflowmenu) (iOS 27.0+) or [`UINavigationItem.additionalOverflowItems`](https://developer.apple.com/documentation/uikit/uinavigationitem/additionaloverflowitems) (iOS 16.0+, `UIDeferredMenuElement?`, not an array). Reserve the ellipsis for overflow. Anchor confirmation dialogs in the owning view's state rather than attaching presentation to an ephemeral overflow item.
- [`toolbarVerticalBehavior(_:)`](https://developer.apple.com/documentation/swiftui/view/toolbarverticalbehavior(_:)) / [`UIViewController.preferredVerticalBarBehavior`](https://developer.apple.com/documentation/uikit/uiviewcontroller/preferredverticalbarbehavior) (iOS 27.1+) allow justified opt-outs for suitable layouts. The UIKit property is read-only: override it rather than assign to it. Custom containers can forward through `childForPreferredVerticalBarBehavior`; request updates with `setNeedsUpdateOfVerticalBarConfiguration()`. Keep the preference stable; temporarily hide bars with visibility APIs.

For a necessary custom bar, Apple documents [`UIView.LayoutRegion.bar(onEdge:extent:)`](https://developer.apple.com/documentation/uikit/uiview/layoutregion/bar(onedge:extent:)-8rmhq) with `layoutGuide(for:)`, or SwiftUI `safeAreaBar`. These position custom content; they do not confer system overflow or tab behavior. Preserve long-press labels, Large Content Viewer support, and accessibility when retaining custom controls. [Apple's custom-bar Q&A](https://developer.apple.com/forums/thread/847835)

## Fold-aware content

The HIG identifies the outer camera region (always present, expands for Live Activities), inner camera region (active while the under-display camera is used), and fold division region (active when partially folded, zero width when flat). Activity and geometry can change without a new scene; ordinary safe areas do not describe every interior region.

[Strike a pose with adaptive layouts](https://developer.apple.com/videos/play/tech-talks/111463/) introduces region queries and arrangement containers. The published SwiftUI method is [`GeometryProxy.reservedRegions(kind:options:layoutDirectionBehavior:)`](https://developer.apple.com/documentation/swiftui/geometryproxy/reservedregions(kind:options:layoutdirectionbehavior:)); UIKit uses `UIView.reservedRegions(kind:options:)`. Query `.division` or `.occlusion` in the relevant view's coordinate space. [`ReservedRegion`](https://developer.apple.com/documentation/swiftui/reservedregion) / [`UIView.ReservedRegion`](https://developer.apple.com/documentation/uikit/uiview/reservedregion) report a frame, margins, activity, and an opaque identity; use those margins for grouped content and identity when tracking a region across updates. `.includeInactive` permits anticipating a region's layout; check `isActive` before treating it as an active obstruction. SwiftUI's default `.mirrors` accounts for RTL layout; use `.fixed` when manually calculating in unmirrored coordinates. The method prose and inactive-query option currently disagree about filtering, so inspect SDK/runtime behavior if it matters to the implementation.

System alerts, menus, sheets, split views, and grids already make useful adjustments; continuously scrolling content is not displaced as one unit. Favor small corrections for custom controls. In a tabletop layout, viewing content can occupy the top and controls the bottom; in book-like layouts, keep related content grouped and usable around the division.

For two related content areas, [`ArrangementView`](https://developer.apple.com/documentation/swiftui/arrangementview) offers split and overlay styles with axis constraints; the default automatic style resolves to split. [`UIArrangementViewController`](https://developer.apple.com/documentation/uikit/uiarrangementviewcontroller) provides primary/secondary controllers and state (`isHidden`, `splitAxis`, `zIndex`). In overlay style with an active division, the primary occupies trailing/bottom and the secondary leading/top; otherwise the primary overlays the secondary. `overlayArrangementEdge(_:)`, `splitArrangementLayoutRatio(_:)`, and split layout size preferences tune the composition; ratio and size preferences interact with `layoutPriority`, so do not assume fixed pane dimensions. These APIs start at iOS 27.1 and organize content rather than replacing navigation. Read their current declarations and availability before implementation. The HIG and recap say keep navigation outside arrangements; the preparation guide also warns against placing an arrangement inside `NavigationSplitView`, lists, or scroll views. Use a supported composition such as an arrangement within a `NavigationStack`, avoid nesting competing split containers, and verify mixed containment rather than assuming every nesting works.

## Scenes and multiple displays

[Multiple displays and scenes](https://developer.apple.com/videos/play/tech-talks/111464/) separates hinge interactions from layout. [`onHingeChange(isEnabled:_:)`](https://developer.apple.com/documentation/swiftui/view/onhingechange(isenabled:_:)) receives previous and current `DeviceHingeContext`; its optional hinge carries a SwiftUI `Angle`. [`UIHingeInteraction`](https://developer.apple.com/documentation/uikit/uihingeinteraction) receives interaction/update values; `UIHinge.angle` is in radians and its status can be `.unknown`. A nil hinge can mean unsupported hardware or a view leaving a hierarchy that supplies hinge data. Both APIs start at iOS 27.1; avoid retain cycles in callbacks. Use region and arrangement APIs for layout rather than an angle threshold. Hinge callback frequency and precision are system-controlled.

Opening and closing normally resize the existing scene; they do not imply process teardown. [Apple's Group Lab recap](https://developer.apple.com/forums/thread/847644) says standard input, scroll position, and AVKit playback generally survive; test custom view identity and state rather than adding reset logic. `UserDefaults` / `@AppStorage` are app-wide, so use appropriate per-scene ownership for independent navigation and drafts. Real scene disconnect/reconnect still needs the app's restoration path.

Duo supports multiple instances through the existing scene APIs and `UIApplicationSupportsMultipleScenes`. New windows cannot be created on the outer display; handle activation errors and unavailable actions. On closing, the most recently active scene continues and other scenes become inactive/backgrounded; a full-screen fold alone need not change `scenePhase`. [Scene lifecycle Q&A](https://developer.apple.com/forums/thread/847838)

The written [capture-accessory guide](https://developer.apple.com/documentation/avfoundation/registering-a-camera-capture-accessory-on-iphone-duo) scopes registration to the capture interface. Keep essential controls in the main scene; share state through an observable model or UIKit `userInfo`, retaining the model and registration. SwiftUI `CameraCaptureAccessory(isEnabled:content:)` and UIKit `UISceneAccessory.cameraCapture(sceneConfiguration:userInfo:)` start at iOS 27.1; general registration APIs start at 27.0. UIKit accessory scenes require no separate manifest entry.

Observe availability separately from enabled state and presentation. The system finds the running capture session and chooses presentation; the app supplies neither a display target nor a session to registration. The topmost registration of the same kind wins. Navigation, closing, stopped capture, or leaving the foreground can withdraw content; stop accessory tasks cleanly and unregister when no longer offered. Camera accessories cannot be tested in the simulator. AlarmKit and Live Activities have separate system presentations; do not infer unrestricted two-display rendering.

## Camera apps only

[Build a great camera experience](https://developer.apple.com/videos/play/tech-talks/111465/) describes a virtual front camera that switches between physical inner and outer cameras, sharing 1080p/60 fps and no depth. Selecting physical devices can expose more formats but transfers switching responsibility to the app. Both inner and outer cameras report `.front`; position alone does not identify which faces the person using a particular display.

The outer front camera's [tech specs](https://www.apple.com/iphone-duo/specs/) list 4K Dolby Vision at up to 60 fps and 1080p slo-mo at 120 fps, **not 4K at 120 fps**. Inspect each device's `formats`, frame-rate ranges, and supported depth formats rather than combining separate maximum capabilities into an assumed format.

The written [camera-direction guide](https://developer.apple.com/documentation/avkit/choosing-a-camera-by-the-direction-it-faces) confirms that front discovery with `.builtInWideAngleCamera` / `.builtInUltraWideCamera` yields the virtual front device; `activePrimaryConstituent` is nil until capture runs. Discover physical `.builtInOuterUltraWideCamera` / `.builtInInnerUltraWideCamera` through a discovery session.

Create and retain an [`AVCaptureDeviceDirectionCoordinator(view:deviceTypes:changeHandler:)`](https://developer.apple.com/documentation/avkit/avcapturedevicedirectioncoordinator) on the main actor for each preview/display. Its direction map is initially empty until the first callback. It excludes virtual front, external, Continuity, and Desk View devices. Resolve Sendable device descriptors on the capture actor; they are not reservations, so handle stale identifiers and input failures while preserving/restoring the existing camera. Keep the current camera if it still faces the viewer. Reconfigure one video input and mask preview until frames arrive.

On input changes, recreate `AVCaptureDeviceRotationCoordinator` and reapply connection mirroring: check `isVideoMirroringSupported`, disable automatic adjustment, then set mirroring for the chosen direction. [`dynamicAspectRatio`](https://developer.apple.com/documentation/avfoundation/avcapturedevice/dynamicaspectratio) is an optional, read-only iOS 26+ property; `videoGravity` still controls framing. [`isCameraSensorOrientationCompensationEnabled`](https://developer.apple.com/documentation/avfoundation/avcapturephotooutput/iscamerasensororientationcompensationenabled) belongs to `AVCapturePhotoOutput` (iOS 26+). Disable compensation only with correctly implemented rotation and supported output behavior. Verify recording and still-photo orientation on hardware.

The virtual front camera's handover can drop frames without a dropped-frame reason or interruption notification; `AVCaptureVideoDataOutput` timestamps become discontinuous and switching latency depends on configuration. Real-time processing must tolerate the gap and refreshed camera metadata. [Camera continuity Q&A](https://developer.apple.com/forums/thread/847766)

An `ARSession` qualifies as active capture for a camera accessory according to Apple's [corrected ARKit answer](https://developer.apple.com/forums/thread/847744). The accessory is ancillary content for another viewer, not a second complete AR experience. Do not start a competing `AVCaptureSession` merely to qualify for it.

## Motion-driven features only

[`CMMotionManager.deviceMotionBody`](https://developer.apple.com/documentation/coremotion/cmmotionmanager/devicemotionbody) (iOS 27.0+) accepts an optional `CMBodyIdentifiable`; `UIView` conforms. Set it to the tracked view to transform attitude, rotation rate, gravity, and acceleration for that display; nil selects hardware coordinates. The property documentation permits a motion manager for each tracked view. Do not derive layout from raw chassis orientation.

The current [`CMBodyIdentifiable` documentation](https://developer.apple.com/documentation/coremotion/cmbodyidentifiable) describes Split View support, while the Group Lab recap limits display-relative mapping to full-screen scenes. Treat multitasking behavior as a dated documentation conflict and verify the actual SDK and hardware before relying on it.

## Hardware facts

Apple's [tech specs](https://www.apple.com/iphone-duo/specs/) list a 7.6-inch inner display (1878×2670 at 430 ppi), a 5.4-inch outer display (1398×2034 at 460 ppi), and a side-button fingerprint sensor. Audit cached aspect ratios, status-bar heights, and hardcoded “Face ID” copy. These values are not layout breakpoints or a device-detection scheme.

Native Apple documentation does not establish support in a React Native package, Expo release, Flutter plugin, or browser. Verify those layers using [frameworks.md](frameworks.md).

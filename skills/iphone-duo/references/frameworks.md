# Implementation by framework

Read the section matching the repository. These are migration approaches; only the linked Apple reference establishes Duo-specific native behavior. Check dependency versions and their official documentation before choosing APIs or upgrades.

Framework documentation and source reviewed on **2026-09-30**. Versioned examples below distinguish released SDK 57 from SDK 58 beta; recheck the installed packages and build logs before applying them.

## SwiftUI and UIKit

Trace the scene root and existing navigation containers before changing presentation. Read the layout, bars, and fold-aware sections of [apple-platform.md](apple-platform.md) for the platform rules and new symbols.

Keep selection, drafts, and navigation identity in the existing model layer when swapping adaptive presentations. Inspect whether conditional roots reconstruct a model or repeat work. In UIKit, trace containment and constraints when a controller changes size; check custom views and embedded hosting controllers as well as the root.

Prefer a fix in the existing shared component over introducing a second app shell. If the app uses custom navigation for a product reason, adapt it deliberately and verify all actions. Do not promise the native system's new bar behavior merely because a view resembles a tab bar.

Check both local and CI compilers before adopting new SDK symbols. A supported deployment target is separate from the SDK used to build. Keep older-device behavior testable, and do not make upgrading the whole project the first step when an existing API solves the defect.

## React Native and Expo

Apple's Duo behavior is decided in the native layer; JavaScript only sees its results. Map each Apple rule in [apple-platform.md](apple-platform.md) to the layer that owns it before editing.

The SDK tier is a build decision. For EAS Build it is set by the `image` in `eas.json` (or the `auto` alias). [Expo's infrastructure page](https://docs.expo.dev/build-reference/infrastructure/), checked 2026-09-30, lists `macos-tahoe-26.6-xcode-27.1` with **Xcode 27.1 beta (27A9269)**; select that explicit image when testing the 27.1 SDK. The `sdk-58` image carries Xcode 27.0, while `latest` / `sdk-57` still carry Xcode 26.6. These aliases can move: check the "Spin up build environment" log and record the actual compiler and SDK. Local `npx expo run:ios` uses the selected local Xcode; Expo Go and an existing development client keep whatever SDK built them. An EAS Update never changes the tier. Do not describe a beta toolchain as a final release or claim Duo-native behavior from the Expo SDK version alone.

An orientation setting does not establish fixed window geometry. `orientation: "portrait"` writes supported orientations, but compatibility behavior and the SDK-linked behavior differ; apply the distinction in [apple-platform.md](apple-platform.md) and test the inner display and Split View. [Expo's iOS 27 orientation guidance](https://docs.expo.dev/versions/v58.0.0/sdk/screen-orientation/#orientation-locks-on-ios-27-and-later) says `lockAsync` may be refused while resizable, and `getOrientationAsync` may not describe the window's shape. `ios.requireFullScreen` writes the deprecated `UIRequiresFullScreen` key. Apple's updated [TN3192](https://developer.apple.com/documentation/technotes/tn3192-migrating-your-app-from-the-deprecated-uirequiresfullscreen-key) explains that the key and SDK linkage can select a discrete resize mode; it is not an exemption from resizing. Inspect the generated plist, including any `UIRequiresFullScreenIgnoredStartingWithVersion`, before changing these settings.

Use the window, not the screen. React Native [0.87's `RCTDeviceInfo.mm`](https://github.com/react/react-native/blob/v0.87.0/packages/react-native/React/CoreModules/RCTDeviceInfo.mm) still reads screen dimensions and scale from `UIScreen.mainScreen`. [0.88.0-rc.0](https://github.com/react/react-native/blob/v0.88.0-rc.0/packages/react-native/React/CoreModules/RCTDeviceInfo.mm), used by SDK 58 beta, instead reads the key window's screen with a fallback; screen bounds still do not equal app space. [`useWindowDimensions`](https://reactnative.dev/docs/usewindowdimensions) updates window dimensions and font scale. Replace screen-based layout math and cached module-level `Dimensions.get(...)` values with live window values, and measure a column, modal, or pane through `onLayout` instead of treating the whole window as available space. SDK 58's Expo packages also migrate away from `UIScreen.main`; inspect custom modules for older geometry assumptions.

Do not select layouts from `Platform.isPad` or `expo-device` `deviceType`: Duo remains a phone, and enabling an iPad target family is not required for Duo support ([Apple Frameworks Engineer](https://developer.apple.com/forums/thread/847945)). Derive layout from measured container width with breakpoints explained by content. JavaScript can receive iOS size classes through `expo-screen-orientation`'s `ScreenOrientationInfo.horizontalSizeClass` and `verticalSizeClass`; its documented listener is orientation-based, so verify updates during resizing and display changes before using it as a live trait observer. If the installed API cannot supply the scene-local signal a flow needs, expose it through a small Expo Module and keep a measured-size fallback.

Treat safe-area insets per edge. Apple's insets are asymmetric because controls sit along one edge, and along each app's outer edge in Split View. [`react-native-safe-area-context`'s provider](https://github.com/AppAndFlow/react-native-safe-area-context/blob/main/ios/RNCSafeAreaProvider.m) measures its own native view's `safeAreaInsets` and reports `top`, `right`, `bottom`, and `left`; the provider's placement matters inside modals and native containers. Audit for `insets.left * 2`, hardcoded status-bar heights, `StatusBar.currentHeight`, and React Native's core `SafeAreaView`. [Expo's safe areas guide](https://docs.expo.dev/develop/user-interface/safe-areas/) documents provider setup, which the default Expo Router template supplies. Check native containers' automatic content insets before adding padding twice.

Native containers may adapt automatically; JavaScript bars need explicit layout changes. Apple's vertical-bar behavior belongs to container-managed bars in a binary built with the 27.1 SDK. Expo Router's native stack and [`NativeTabs`](https://docs.expo.dev/router/advanced/native-tabs/) use native UI; use `expo-router/native-tabs` on SDK 58, or `expo-router/unstable-native-tabs` on SDK 54–57. Side placement still depends on the compiled SDK and installed native libraries, so verify on the Duo simulator. [React Navigation's JavaScript tabs](https://reactnavigation.org/docs/bottom-tab-navigator/) support configurable placement, but do not acquire Apple's system behavior merely through a plist change. Adapt an existing custom bar only when the product requires it. `headerLeft` / `headerRight` custom views may default to horizontal-only or overflow; test them against Apple's bar guidance.

SDK 58 beta also adds native SwiftUI navigation through `@expo/ui`, including `NavigationStack`, `Toolbar`, and `NavigationSplitView` ([release notes](https://expo.dev/changelog/sdk-58-beta), [SwiftUI integration](https://docs.expo.dev/versions/v58.0.0/sdk/ui/swift-ui/)). This provides another native integration path when it fits the app; it does not migrate existing JavaScript navigation. Preserve containment and state, and test the `Host` / `RNHostView` measurement boundary. When upgrading Router to SDK 58, follow its [migration guide](https://docs.expo.dev/router/migrate/sdk-57-to-58/): tabs and drawers show only declared screens, `freezeOnBlur` no longer has an effect, and custom navigator / React Navigation compatibility APIs have changed. These changes can affect an adaptive presentation independently of Duo.

Scene lifecycle support depends on the Expo SDK version. [Expo's scene life-cycle guide](https://expo.fyi/ios-scene-lifecycle) documents SDK 58's generated `SceneDelegate` and scene manifest; custom app-delegate integrations must follow its callback rules. SDK 57 retains the legacy lifecycle by default, but `expo@57.0.23` or newer plus the current `expo-build-properties` can opt in through `ios.enableSceneSupport: true`. That opt-in uses the built-in `EXExpoAppSceneDelegate`; it does not generate SDK 58's `SceneDelegate.swift`. Inspect the generated native result and rebuild. A scene lifecycle does not by itself enable multiple app windows: the SDK 58 example sets `UIApplicationSupportsMultipleScenes` to `false`. Treat multiple-window creation and per-scene state isolation as a separate native feature request.

Reserved regions, arrangements, and the hinge originate in native APIs. Do not assume a JavaScript wrapper exists in the installed packages: check their current docs and source for the exact capability. Ordinary resizing does not need a hinge bridge. When a flow needs a missing signal (for example keeping a composer clear of the fold), write a narrowly scoped Expo Module in Swift, guard runtime availability with `#available`, and protect references to newer symbols when building with an older SDK; an availability check alone cannot make an older compiler recognize them. Ship persistent plist or build-setting changes through a config plugin and retain older-device fallbacks. Confirm any experimental module API against the installed Expo version before choosing it.

Check camera and biometric assumptions. [`expo-camera`](https://docs.expo.dev/versions/v58.0.0/sdk/camera/) exposes `facing="front"`, but that prop alone does not prove Duo camera handoff or direction-aware capture. Inspect the installed native discovery and session code, then test preview, capture, recording, and transitions on hardware. SDK 58's lens API returns `LensInfo` objects: pass `deviceType` to `selectedLens`, and use `localizedName` only for display. Do not hardcode new physical-camera identifiers from a talk into JavaScript. For biometrics, branch on [`supportedAuthenticationTypesAsync()`](https://docs.expo.dev/versions/v58.0.0/sdk/local-authentication/) instead of hardcoding "Face ID" copy, and keep `NSFaceIDUsageDescription` (`faceIDPermission`) for devices that use Face ID.

For Expo, determine whether the native project is generated or maintained manually. [Expo's Continuous Native Generation guide](https://docs.expo.dev/workflow/continuous-native-generation/) explains that prebuild can replace manual native edits. The [SDK 57 CLI source](https://github.com/expo/expo/blob/sdk-57/packages/@expo/cli/src/prebuild/index.ts) and current CLI source set clean generation by default, with `--no-clean` restoring additive generation; the general CNG page still describes the older default. Check the installed `npx expo prebuild --help` before running it. In generated projects, use supported configuration or a config plugin for persistent native changes. Do not run prebuild over unrelated native work.

Inspect the development-client or production build path. JavaScript checks and Expo Go do not prove that a custom native integration compiles in the shipping app or that the binary was linked with the intended SDK. SDK 58 is still beta as of this review and uses React Native 0.88 RC; React Native's current stable documentation is 0.87 ([version index](https://reactnative.dev/versions.html)). [Expo's simulator guide](https://docs.expo.dev/workflow/ios-simulator/) covers Xcode 27's Device Hub. Use an installed CLI version with Device Hub support, verify the selected Xcode and 27.1 simulator runtime, then discover the Duo destination for `npx expo run:ios`; do not hard-code it.

## Flutter

Flutter's [adaptive-app guidance](https://docs.flutter.dev/ui/adaptive-responsive/general) distinguishes available window size from local layout constraints. Use `MediaQuery.sizeOf` or `LayoutBuilder` according to the space the widget actually owns. Review the project's breakpoints, inherited media data, navigation, and state before changing layout branches.

Preserve selected routes, scroll controllers, text controllers, and ongoing tasks across rebuilds. Check safe-area and keyboard handling in both the widget tree and iOS host. A global width can be wrong inside a nested navigator or constrained pane.

Do not assume Android folding features or a plugin's posture API is implemented for iPhone Duo. Confirm support in the installed Flutter engine and plugin code or official release notes. If a native bridge is needed, verify its Swift side against Apple's SDK and keep unavailable capabilities explicit. Run analysis, relevant widget tests, and a real iOS build.

## Web, PWA, Capacitor, and other web wrappers

First distinguish Safari from a native web view and identify which layer owns navigation, keyboard adjustment, and insets. Fix layout against the actual container. Inspect fixed overlays and the composer or form while the keyboard opens and the viewport resizes.

CSS [`env()`](https://developer.mozilla.org/en-US/docs/Web/CSS/Reference/Values/env) provides environment values including safe-area insets and documents viewport-segment variables. Their existence in CSS documentation does not prove support in the user's Safari or embedded engine. Check compatibility for the actual browser version and feature before using it, and retain a usable layout when a value or feature is unavailable.

Apple's [official Duo Group Lab recap](https://developer.apple.com/forums/thread/847644) says Viewport Segments and Device Posture can be tested experimentally in iOS 27.1 by enabling their flags in Settings → Apps → Safari → Advanced → Feature Flags. This is opt-in testing, not a promise of default production support. The WebKit standards discussions for [Viewport Segments](https://github.com/WebKit/standards-positions/issues/327) and [Device Posture](https://github.com/WebKit/standards-positions/issues/328) track the proposals; they do not establish Safari or `WKWebView` shipping support. Verify both the actual browser and embedded wrapper, and keep a fallback when the flags or APIs are unavailable.

Do not infer hinge support from ordinary viewport resizing or a successful CSS parser check. A wrapper may need a verified native integration for platform-only behavior. Test inside the built iOS wrapper when that is the delivered product; desktop browser checks cover only part of the result.
